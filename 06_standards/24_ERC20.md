## 3. 先讲结论

**ERC20 是以太坊上"可同质化代币"的事实标准** —— USDT、USDC、UNI、LINK 全是 ERC20。它只规定接口和事件,不规定实现细节,所以才能成为全行业的"插槽"。

## 4. 合约设计

### 4.1 IERC20 接口规格 (`src/raw/IERC20.sol`)

```solidity
interface IERC20 {
    event Transfer(address indexed from, address indexed to, uint256 value);
    event Approval(address indexed owner, address indexed spender, uint256 value);

    function totalSupply() external view returns (uint256);
    function balanceOf(address account) external view returns (uint256);
    function transfer(address to, uint256 amount) external returns (bool);
    function allowance(address owner, address spender) external view returns (uint256);
    function approve(address spender, uint256 amount) external returns (bool);
    function transferFrom(address from, address to, uint256 amount) external returns (bool);
}
```

### 4.2 状态变量(两个实现都至少要有)

| 变量 | 类型 | 含义 |
|------|------|------|
| `totalSupply` | `uint256` | 总发行量 |
| `balanceOf[addr]` | `mapping` | 每个地址的余额 |
| `allowance[owner][spender]` | `mapping` | owner 授权给 spender 的额度 |

### 4.3 三种"动钱"的方式

| 操作 | 谁付 gas | 谁的代币流出 |
|------|---------|-------------|
| `transfer(to, amount)` | msg.sender | msg.sender |
| `approve(spender, amount)` | msg.sender(只是登记授权,不动钱) | — |
| `transferFrom(from, to, amount)` | msg.sender(spender) | from |

记住:**`transferFrom` 是"代扣",必须先有 `approve`**。

## 5. 代码拆解

### 5.1 raw 实现 —— 看清每条赋值 (`src/raw/ERC20.sol`)

#### transfer:本人转账,最简单
```solidity
function transfer(address recipient, uint256 amount) public override returns (bool) {
    balanceOf[msg.sender] -= amount;
    balanceOf[recipient] += amount;
    emit Transfer(msg.sender, recipient, amount);
    return true;
}
```
要点:
- 0.8+ 自带溢出检查,余额不够会自动 revert
- 必须发 `Transfer` 事件,这是 ERC20 标准

#### approve + transferFrom:两步授权代扣
```solidity
function approve(address spender, uint256 amount) public override returns (bool) {
    allowance[msg.sender][spender] = amount;
    emit Approval(msg.sender, spender, amount);
    return true;
}

function transferFrom(address sender, address recipient, uint256 amount)
    public override returns (bool)
{
    allowance[sender][msg.sender] -= amount;  // 先扣授权额度
    balanceOf[sender] -= amount;              // 再动 sender 的钱
    balanceOf[recipient] += amount;
    emit Transfer(sender, recipient, amount);
    return true;
}
```
要点:
- `transferFrom` 里 `msg.sender` 是 spender(被授权方),`sender` 是 owner
- 注意三条减法的顺序:先扣 allowance,再扣 balance

#### mint / burn:教学用,生产环境一定要权限
```solidity
function mint(uint256 amount) external {
    balanceOf[msg.sender] += amount;
    totalSupply += amount;
    emit Transfer(address(0), msg.sender, amount);  // 铸造视为从 0 地址转入
}

function burn(uint256 amount) external {
    balanceOf[msg.sender] -= amount;
    totalSupply -= amount;
    emit Transfer(msg.sender, address(0), amount);  // 销毁视为转到 0 地址
}
```

### 5.2 oz 实现 —— 继承 + 重写就够了 (`src/oz/ERC20Token.sol`)

```solidity
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract ERC20Token is ERC20 {
    uint8 private _decimals;

    constructor(string memory name_, string memory symbol_, uint8 decimals_)
        ERC20(name_, symbol_)
    {
        _decimals = decimals_;
    }

    function decimals() public view override returns (uint8) {
        return _decimals;
    }

    function mint(uint256 amount) external { _mint(msg.sender, amount); }
    function burn(uint256 amount) external { _burn(msg.sender, amount); }
}
```
要点:
- `transfer` / `approve` / `transferFrom` 完全继承自 OZ 的 `ERC20`,不用自己写
- OZ 默认 `decimals = 18`,这里 override 出来让构造时可配
- OZ 提供 `_mint` / `_burn` 内部函数,自己只暴露薄薄一层

### 5.3 对照看 —— raw vs oz

| 维度 | raw | oz |

## 8. 常见错误排查

### 错误 1:`transferFrom` 直接 revert,没有显式原因

- **常见原因**:没有先 `approve`,或 allowance 已被用光
- **解决步骤**:在调用 `transferFrom` 前打印 `allowance(owner, spender)` 确认额度
- **验证方式**:`testApproveAndTransferFrom` 演示了完整两步流程

### 错误 2:`transfer` 时 balanceOf 不够,但合约没报错

- **常见原因**:用了 Solidity 0.7 以下版本,溢出不检查
- **解决步骤**:升级到 0.8+,或在 `transfer` 里加 `require(balanceOf[msg.sender] >= amount)`
- **验证方式**:`testTransferFail` 用 `vm.expectRevert()` 校验余额不足必须 revert

### 错误 3:OZ 版部署后 `decimals()` 返回值不对

- **常见原因**:忘记 override `decimals()`,OZ 默认返回 18
- **解决步骤**:在子合约里 `function decimals() public view override returns (uint8) { return _decimals; }`
- **验证方式**:部署时传不同 `decimals_` 值,再 `cast call <addr> "decimals()(uint8)"` 验证

### 错误 4:把 `mint` 直接暴露成 external 上了主网

- **常见原因**:照搬教学代码,没有加权限控制
- **解决步骤**:生产环境必须 `onlyOwner` 或彻底封闭 mint
- **验证方式**:用 OZ `Ownable`(参考第 12 课 modifier) 或固定 supply 的构造函数

## 8.5 本课安全边界

> 集中安全知识见第 20 课(常见漏洞与防护),本节只列**与 ERC20 直接相关**的坑点,避免在写第一个 token 时翻车。

### 坑 1:`mint` / `burn` 暴露为 external,任何人都能铸

**现象**:教学代码里 `function mint(uint256 amount) external { ... }` 没加权限,主网部署后任何人调一次 `mint(1e30)` 直接发币。

**修复**:
```solidity
import {Ownable} from "@openzeppelin/contracts/access/Ownable.sol";

contract ERC20Token is ERC20, Ownable {
    function mint(uint256 amount) external onlyOwner { _mint(msg.sender, amount); }
    function burn(uint256 amount) external onlyOwner { _burn(msg.sender, amount); }
}
```

**或**彻底封闭 mint,固定 supply:
```solidity
constructor(uint256 totalSupply) {
    _mint(msg.sender, totalSupply);
}
// 不暴露任何 mint 函数
```

### 坑 2:`approve` 前后值插队(经典 ERC20 攻击)

**现象**:Alice 准备把 spender 的 allowance 从 100 改成 50。Alice 先 `approve(spender, 50)`,但 spender 看到交易池里还有 100 → 在 Alice 的 50 交易上链前调 `transferFrom(Alice, ..., 100)` → 拿到 100 → Alice 的 50 上链 → spender 再 `transferFrom(Alice, ..., 50)` → **总共转走 150**。

**修复**(OZ `ERC20` 自带):
```solidity
function increaseAllowance(address spender, uint256 addedValue) external returns (bool);
function decreaseAllowance(address spender, uint256 subtractedValue) external returns (bool);
```

调用 `decreaseAllowance(spender, 50)`(从 100 减到 50)就**安全**,因为当前值就是 100。

### 坑 3:`USDT` 这种 `transfer` 不返回 bool

**现象**:USDT 的 `transfer` / `transferFrom` **失败时不 revert,只 return false**,但接口签名要求 `returns (bool)`。直接写 `IERC20(token).transfer(to, amt)` 不检查返回值,**转账失败也无感知**。

**修复**:
```solidity
import {SafeERC20} from "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

using SafeERC20 for IERC20;
IERC20(token).safeTransfer(to, amt);   // 不 bool 返回,revert 失败
```

### 坑 4:Fee-on-Transfer / 通胀型 token

**现象**:某些 token 在 transfer 时扣 1% 手续费(如 PAXG),用户实际收到 99%。如果你在合约里写:
```solidity
token.transferFrom(user, me, amount);
balanceOf[user] -= amount;   // ← 实际 user 只花了 99,这里却记 100
```
→ **记账出错**。

**修复**:
- **收款方用 `balanceOf` 差值**:转账前 `b0 = token.balanceOf(me)`,转账后 `b1`,真实到账 = `b1 - b0`
- 不要假设 transfer 前后 `amount` 不变

### 坑 5:零地址转账 = 钱永久丢失

**现象**:`transfer(address(0), 100)` 把 100 token 烧到 0 地址,没人能找回(USDT 历史上多次发生)。

**修复**:
```solidity
require(to != address(0), "ERC20: transfer to zero address");
```

OZ 5.x 版的 `ERC20._update` 已经内置这个检查。

### 坑 6:整数溢出

**现象**:`totalSupply = uint256(-1)` 后 `balanceOf[A] += 1` 会从 0 开始(在 0.8 之前)。Solidity **0.8+ 自动 revert**,但 0.7 及以下要小心。

**修复**:用 0.8+(本项目已经是)。老项目迁移:加 `unchecked` 显式标注,或者 `using SafeMath`。

### 关键防御清单

| 风险 | 防御 |
|------|------|
| 公开 mint | `onlyOwner` 或彻底封闭 |
| approve 插队 | 用 `increaseAllowance` / `decreaseAllowance` |
| USDT 不返回 bool | `SafeERC20.safeTransfer` |
| Fee-on-Transfer | 用 `balanceOf` 差值,不要相信 `amount` |
| 零地址转账 | 加 `require(to != address(0))` |
| 重入(approve / transferFrom) | OZ 5.x 默认 Checks-Effects-Interactions,无重入风险 |
| 事件缺失 | 必须 emit `Transfer` / `Approval`,否则 Etherscan 看不到 |

> 这些坑点在第 20 课会系统讲;ERC20 课再列一遍是因为**这是写 token 最常犯的错**。

## 9. 本节总结

- ERC20 标准的核心是 **6 个函数 + 2 个事件**,接口规定的是"行为契约"
- `balanceOf` / `allowance` / `totalSupply` 三大状态变量足以表达全部状态
- `transfer` 自付 / `transferFrom` 代扣,中间用 `approve` 登记授权
- raw 版让你看清每条赋值,oz 版让你少写代码、走审计过的路径
- 生产环境务必给 `mint` / `burn` 加权限,默认 OZ 的 `Ownable` 是常用搭配
- 写第一个 token 最常踩的坑:mint 公开、approve 插队、USDT 非 bool、Fee-on-Transfer、零地址转账
